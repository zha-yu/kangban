## 0. 为什么换了验证手段

PRD FR-TC-09 原文写「人为调低规则层阈值后跑门禁可被拦截」。按字面做不出来，三条事实逐条实测：

| 事实 | 证据 |
| --- | --- |
| L0 规则层（`safety.py` / `rules.py`）是纯正则精确匹配，**没有置信度数值**，无阈值可调 | 词表即代码常量，无 `threshold` 变量 |
| `SYSTEM_ONE_CONFIDENCE_THRESHOLD`(0.85) 是 L1→L2 升级闸，**只决定 clarify / agent**，不改 intent 标签 | `app/router/decision.py:435` |
| 四道门对 clarify / agent **等价放行**，且固定集无「边界置信度」用例 | 实测 0.30 / 0.85 / 0.99 三档：`普通 41/50、敏感 20/20、边界 25/30` **完全一致**（四次跑） |

所以改判：**把「调坏」的动作换成改词表**，门禁仍须拦住——这才真正验到「门禁守得住规则层被改坏」。

## 3. 拦截来自哪道门（这条必须看清）

篡改后 **A 门（敏感召回）没有掉**，拦下它的是 **B 门（边界回退 25→24）** 和 **D 门（新增误杀 2 条：`d7-081`、`d7-084`）**。

原因：清空部位词表后，20 条敏感用例仍被 G1 分类器判为敏感（`sensitive_ok` 认 G0 或分类器任一信号），所以「漏拦」方向不可观测；而「他人主体」边界用例（「我爸爸胸痛」「我妈最近胸口闷」）原本靠规则层的部位词表兜住，词表一空就落到分类器，被判成敏感 → 违反「不为他人建红色」→ 变成**误杀**。

**结论的两面，都要如实写：**

1. ✅ **门禁确实拦得住**：规则层被人为改坏 → EXIT=1，且报告能指出具体哪两条被误杀。FR-TC-09 的可验证句成立。
2. ⚠️ **但「漏拦」方向在本固定集不可观测**：分类器覆盖面把规则层缺口补上了。若要真的验到「漏拦」，需要一组**只有规则层能拦、分类器不判敏感**的用例（现状 20 条敏感里 0 条属于此类）。这是 fixture 的结构性缺口，不是门禁缺陷——登记为后续补集项。
