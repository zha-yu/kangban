## 三、逐段要点与话术

### 1. 结论先行（0:00–0:35）

- 身份与范围一句话：「我是 A2，Day 4 负责 W3——信令追加与对话闭环，写作域是 `signaling.py`、`llm_service.py`、`dialogue_service.py`、`core/context.py` 加测试。」
- 状态一句话：「三项交付 X 项完成、Y 项部分完成，[pytest 数字] 全绿，没有越界改动。」
- 对里程碑一句话：「M3 要的『打开 5 秒立起并开口说话』，A2 侧靠 greeting 不依赖 LLM 这一段兜住了。」

### 2. 我负责哪一段（0:35–1:10）

- 上游：A1 的身份判定结果（voice / confirm / generic 三态）、A3 的 ASR FINAL 回调入口。
- 下游：pad 字幕与口型消费 `tts_text`，A4 在主链上打点。
- 关键边界：「迁移、`config.py`、`webrtc.py`、前端我一律不动；`LLM_*` 字段报 A3 统一录入；C5 是 C2 的追加，合入前已在 task-a2 计划补了变更记录。」

### 3. 三块交付（1:10–3:15）

**3.1 C5 身份级联信令（约 45s）**

- 在 C2 消息表上**追加**四类消息：`identity_ask`、`identity_confirm`、`identity_result`、`client_diag`，原类型与方向零改动。
- 30 秒计时**从服务端 `identity_ask` 实际发送成功起算**，不是前端收到或渲染时起算；断线要取消计时任务。理由：pad 卡顿、后台挂起不能左右身份结论。
- 异常口径：`ask_id` 错配、重复 confirm、候选集外 `elder_id` 一律**忽略 + warn**，不回 error、不关连接——沿 C2 既有惯例，报错反而会暴露候选信息并打断会话。
- 每个身份判定轮次**只下发一次** `identity_result`；generic 恒 `elder_id=None`，不下发 cosine/embedding。
- `client_diag` 只做枚举校验 + 脱敏日志，不落库、不转发、不进 metrics（打点归 A4）。

**3.2 C6 对话链（约 45s）**

- LLM 适配器：Minimax 走 OpenAI 兼容端点，httpx 直连**不引 SDK**；首次之后最多再重试 2 次（总请求 ≤3），只对瞬态错误退避，最后一次失败不再 sleep。
- 降级：失败后返回固定长者可读模板，`degraded=true` 随 `tts_text` 下发，页面不白屏不静默（FR-DLG-05）；日志只留 trace、错误分类、尝试序号，不回显 Authorization 和响应体。
- 上下文：固定人设前缀（字节稳定，保 cache）+ 动态身份/称呼/时间单独成消息 + Redis 最近 **5 轮**（= 10 条 user/assistant，本轮 user 不重复计入）。
- generic 的安全边界不是靠 prompt 自觉，而是**不注入个人上下文、不接记忆/健康/用药端口**。

**3.3 thread 闸门与 greeting（约 35s）**

- thread 由服务端按 `(elder_id, session_seq)` 建，客户端和模型传的 `elder_id`/`thread_id` 一律丢弃。
- 顺序固定：**身份级联 → 建/切 thread → 读该 thread 历史 → LLM → 写回**，保证"未确认身份不读个人上下文"。
- 换人：先写旧 thread `ended_at`，再建新 thread，Redis key 跟 `thread_id` 走，历史不互读。
- greeting 取 `personas.greeting` 直送 TTS，**不调 LLM**，这是"5 秒开口"的前提。

### 4. 证据（3:15–4:05）

- 单测：`uv run pytest -q` → [待填：X passed]；新增 A2 用例 [待填：N 条]；`ruff check app tests` [待填：通过/有 N 项]。
- 回归：Day 3 C2 的 WS 用例（鉴权、心跳、offer/ice、断线清理、双连接隔离）[待填：全绿/无回归]。
- 联调（14:30–16:30 窗口）三条路径各说一句结论，**没跑通就说没跑通**：
  - 正常：说话 → ASR FINAL → `identity_result(voice)` → thread → Minimax → `tts_text` → 音频轨。
  - 低置信：`identity_ask` → confirm → 一次 `identity_result(confirm)`。
  - 声纹不可用 / 30s 超时：`identity_result(generic)`，回复不带个人记忆，健康/用药请求被拒。
- 契约留痕：C5 属 C2 追加，变更记录已写入 `docs/plans/task-a2-信令WS与鉴权.md`；无未确认的协议变更。

### 5. 风险与需要的支持（4:05–4:40）

只讲 1–3 条，每条带「影响 + 需要谁 + 什么时候要」：

| 风险 | 影响 | 需要谁 |

| # | 可能的问题 | 简明回答（20 秒内） |

| 1 | generic 没有 `elder_id`，thread 怎么建？ | C6 的 `ThreadInfo.elder_id` 是非空 `str`，C5 的 generic 要求 `None`，这是已知冲突。我没有私改契约，也没用默认长者占位；[待填：当前裁决/临时做法]。影响面只是 generic 会话持久化，1v1 主链不受影响。 |
| 2 | 30 秒为什么由服务端计时？ | 前端计时会受 pad 卡顿、切后台、重连影响而误判。服务端从 `ask` 真正发出起算，断线取消任务，超时只发一次 generic 结果，前端不自己兜底。 |

| 4 | LLM 挂了长者听到什么？ | 退避 ≤2（总请求 ≤3）后给固定长者可读模板，`degraded=true`，字幕照常出、TTS 照常播，不白屏不静默。日志里没有密钥和响应体。 |

| 6 | 换人怎么证明不串？ | 顺序是硬约束：身份先于读历史。换人先写旧 thread `ended_at` 再建新 thread，Redis key 跟 `thread_id`，测试用双连接 + 换人用例断言旧 thread 没有新内容。 |
| 7 | 首 token 800ms 达标了吗？ | 本日实现是**非流式**适配，800ms 只是单次观察预算，不是 P95 承诺。实测 [待填：X ms 或"未做真链观察"]。不做没证据的达标声明。 |
| 8 | 动没动别人的文件、有没有偷偷改契约？ | 只动四个文件加测试。`config.py` 字段报 A3 录、迁移不碰、`webrtc.py` 不碰。C5 是 C2 的追加，合入前补了变更记录，没有静默改协议。 |

## 五、需要你补充的信息（不补齐不要上台）

1. **实际完成度**：N00–N10（或 T0–T6）逐项状态——完成 / 部分 / 阻塞 / 未执行，各自证据。代码现状显示 `llm_service.py`、`dialogue_service.py` 尚未出现、`signaling.py` 也没有 identity 消息、task-02 卡还是"未开始"，与你说的"完成 A2"不一致，**先确认是分支没合还是确实未完**。
2. **质量门数字**：`pytest -q` 通过/失败条数、新增用例条数、`ruff check` 是否通过。
3. **联调结果**：14:30–16:30 三条路径（正常 / 低置信 / 声纹不可用或超时）各跑通几次，哪条没跑、卡在哪。
4. **未闭环项与 owner**：B1（generic 空值）、B2（generic thread 标识）、B3（Redis 生命周期）、B4（ASR FINAL seam）、B5（greeting 取值）、B6（403 映射）当前结论。
5. **是否有现场演示**：有则压内容留时间，无则把证据讲细。
6. **听众构成**：只有本组，还是有主理人/产品/测试。有非技术角色时，3.1 的 `ask_id`/`candidates` 这类字段名要减半。
7. **明天的计划**：Day 5 首件事是什么，需不需要在会上要人。

## 六、三条现场纪律

1. **不宣称"全绿"**，除非终端输出就在手边；红项、未执行项要点名，标 blocked 而不是 passed。
2. **Mock 与真链分栏讲**，不要把 Mock 结果说成联调通过——收口会上这一条最容易被抓。
3. **只讲自己写作域**，别人文件的问题只报现象和 owner，不代答、不评价。
