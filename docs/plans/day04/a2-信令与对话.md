## 0. 计划目标与事实口径

本计划供 A2 在项目第四天执行，只覆盖“信令追加与对话闭环”（W3）及其与 A1/A3/A4 的接口协作。计划精确到半小时，逐项列出依赖、步骤、交付物、量化自检；本文件不包含业务代码实现。

### 事实来源与优先级

- 需求和验收以 PRD 为准，实现分层和技术栈以技术设计文档为准；Day04 task cards 与已冻结的 C4–C7 是本日具体分工和接口约定。
- 大纲只用于确认 Day4 的迭代顺序，不用作字段、阈值或接口来源。
- 当前 Day04 细化口径：设备绑定长者 1v1 候选集（恒 1 位）、每会话首轮声纹校验、cosine ≥0.85；这一口径以 Day04 计划 v2.3、Day04 contracts 和同步修订后的 PRD/技术文档为准。
- 通用模式必须允许 elder_id 为空；thread 类型、运行上下文和存储均不得强制非空。
- 本日 P0 对话不引入记忆、Agent Tool 或三级路由；只用稳定人设前缀与 Redis 最近 5 轮。Day4 不做滚动摘要。

- app/audio/signaling.py 已实现 Day3 C2：设备首帧鉴权、心跳、消息转发、连接清理和进程内下行队列。Day4 只在 C2 上追加 C5 消息，不重写鉴权或信令骨架。

- app/main.py 已装配 /ws/signal；A2 不需要重复注册。若确有路由装配需要，只能新增 A2 约定的一行并与 A4 协调。
- 当前代码没有 llm_service.py、dialogue_service.py，也没有 Redis lifespan/provider。配置中已有 deepseek 默认值，但 Day04 task-02 v1.1 和 Day04 README 的主理人决定是 Minimax、OpenAI 兼容端点、httpx 直连且不引 SDK。

### 2.2 必须在契约确认会显式处理的接口缝隙

1. **generic 身份的空值类型**：C5 的 identity_result 允许 elder_id 为 null，ER/技术设计也要求 generic 时 elder_id 可空；但 C6 内部 ThreadInfo 当前写 elder_id: str。若 ThreadInfo 覆盖 generic thread，签字前须将其定义为可空或给出等价类型；不得通过非空约束绕过冲突。
2. **generic thread_id 生成口径**：文档定义 thread_id 服务端生成且基于 elder_id/session_seq，但 generic 没有 elder_id。由 A1/A2 在契约会上明确 generic 会话的内部 thread 标识与 session_seq 归属；不得伪造 elder_id，也不得让客户端/model 提供 thread_id。
3. **ASR final 调用边界**：signaling.py 负责 C2 传输，webrtc.py 属 A3；必须确认 A3 的媒体处理器怎样调用 A2 的对话服务，保持“ASR final 触发业务、partial 只用于字幕”。
4. **Redis 与 greeting 取值**：当前 app 没有 Redis lifecycle provider；C7 也不包含 greeting。确认 Redis 注入/关闭方式及 A2 获取 personas.greeting 的只读服务边界。
5. **LLM 供应商文档同步**：task-02 v1.1 / Day04 README 已确认 Minimax；Day04 技术方案 §5.1 仍列 DeepSeek/Qwen。实现执行时按 task-02 的主理人确认使用 Minimax，但代码合入前须由文档责任人按 AGENTS 修订记录规则同步技术文档，A2 不自行改写基线文档。
6. **确认超时来源**：contracts.md 规定从服务端发出 identity_ask 开始计 30 秒；前端不单独计时；A2 超时后发 identity_result source=generic。

### T1 · C5 信令追加与服务端确认状态机

**前置**：T0 契约签字；C2 既有 15 项 WS 回归用例可运行。

**执行步骤**

1. 在 signaling.py 顶部追加 TypedDict，不改 C2 原有类型或方向。
2. 增加 identity_ask 的服务端下发和 identity_confirm 的接收校验；ask_id 不匹配或身份已定后重复 confirm 时忽略并 warn，不报错、不关闭连接。
3. 30 秒超时从服务端发出 ask 的时刻起算；超时发一次 identity_result(source=generic, elder_id=null)。
4. identity_result 对 voice/confirm/generic 各只下发一次；不向 pad 暴露相似度或 embedding。
5. client_diag 按契约 stage 校验并只写脱敏结构化日志；不落库、不转发、不进 metrics。
6. 确认消息不信任客户端 elder_id；服务端按 A1 结果和冻结候选集核验。
7. 不改变原 WS 首帧鉴权、ping/pong、offer/ice、错误消息和断线清理语义。

**交付物格式**：signaling.py 的增量类型/分支；新增 pytest 用例；C5 冻结和追加记录。

**自检标准**

- 正常 ask → 候选内 confirm → identity_result(confirm) 一条。
- ask 发出后 30 秒无确认 → identity_result(generic, null) 一条。
- ask_id 错配、重复 confirm、候选集外 elder_id 三类都被忽略并留 warn，不改变已定身份。
- client_diag 的合法 stage 有结构化日志；未知 stage 按坏消息处理；日志不含原始语音、token、敏感个人数据。
- Day3 C2 原有 WS 用例全部通过。

### T2 · Minimax 适配器与 LLM 降级

**前置**：T0 vendor/config 约定签字；A3 提供 LLM_* Settings；Minimax 测试 key 仅从本机 .env 读取。

**执行步骤**

1. 新增 llm_service.py，以 httpx 调 Minimax OpenAI 兼容端点，不引入 LLM SDK。
2. 请求参数从 Settings 读取；密钥不进代码、日志、测试夹具或提交。
3. 按 task-02 实现超时/限流错误处理和最多 2 次退避重试；仍失败时返回固定模板话术，并把 C6 的 degraded 标记设为 true。
4. 正常模型回复 degraded 缺省/显式为 false；复用现有 TTS 服务和 WebRTC 音频轨，不新增音频协议。
5. Day4 使用非流式适配即可；task-02 标注的首 token ≤800ms 为本任务预算，记录单次验收观察，不建设延迟指标管线。

**自检标准**

- 成功响应可转换为普通对话文本并送给现有 TTS。
- 超时、限流、连接失败均最多重试 2 次；最终使用模板话术，degraded=true。
- 正常路径 degraded=false；长者可读话术不暴露 HTTP 响应、内部异常或密钥。
- 目标环境下单次响应满足 task-02 所列 ≤800ms 预算；若外部服务当日不满足，记录观察结果并仍须验证降级，不伪造达标数据。
- generic 上下文不含个人记忆；Day4 无记忆来源、无 Agent Tool。

### T3 · Redis 对话轮次与 context 组装

**前置**：T0 冻结 Redis 生命周期接口；T2 有可注入的 LLM 服务；A3/产品提供人设、称呼和时间字段。

**执行步骤**

1. 在 dialogue_service.py 做 Redis 取最近 5 轮、调用 LLM、写回本轮消息的流程；Redis key 使用服务端 thread_id。
2. 在 core/context.py 组装固定人设前缀、称呼、时间、医疗边界及本轮消息；core 只接收参数，不查库。
3. 固定前缀保持字节稳定；Day4 只传 Redis 最近 5 轮，不做滚动摘要、长期记忆或 pgvector 召回。
4. generic 回复使用通用上下文，不携带 persona 私人记忆，不执行健康/用药确认。
5. 记录本轮最近对话，不把原始音频写入 Redis 或数据库。

**交付物格式**：dialogue_service.py、context.py 的单元测试；10 轮上下文验收记录。

**自检标准**

- 连续 10 轮对话后仍能保持称呼；每次给 LLM 的历史最多为最近 5 轮，context 不无限增长。
- 固定前缀重复组装字节一致。
- generic 输入上下文无个人记忆内容，健康/用药动作拒绝；Day4 不读 memory_chunks。
- Redis 客户端有明确注入和关闭方式；不得为每次消息创建未关闭客户端。

### T4 · 服务端 thread gate 与 greeting

**前置**：A1 的 conversation model/迁移已可消费；T0 已明确 generic thread 与空值类型；persona greeting 读取接口已冻结。

**执行步骤**

1. A1 `identity_service` 按 elder_id/session_seq 建立 thread；A2 只消费 A1 `IdentityDecision` 的终态 `thread_id`（经 `identity_decision_to_result` 投影），客户端和模型提供的 elder_id/thread_id 全部丢弃；A1 未回传 `session_seq` 时 A2 留空，不伪造。
2. session_seq 增量和 conversation_threads 创建由 A1 `identity_service` 服务端事务执行；A2 不新增迁移、不建 thread。
3. generic 会话保持 elder_id=null；thread 仍为服务端标识；A2 不伪造“默认长者”填充。
4. 声纹复检发现说话人变化时，由 A1 `identity_service` 给旧 thread 写 ended_at、开新 thread；A2 随新 thread 切换 Redis key，内容不跨 thread。
5. auth_ok 与身份确认完成后，读取 personas.greeting 作为开场白送 TTS；开场白不依赖 LLM。generic 用通用 greeting。
6. 不把个性化记忆接入 Day4；个人对话只用固定人设和 Redis 最近 5 轮。

**交付物格式**：dialogue/thread 编排实现；线程生命周期与 greeting 集成测试；A1/A3 依赖接口记录。

**自检标准**

- client/model 伪造 elder_id 或 thread_id 不会改变服务端身份；对伪造/跨长者 thread 请求返回 403（AC-39）。
- 每次新会话由 A1 `identity_service` 建立 thread；speaker 身份变化时 A1 写旧 ended_at、开新 thread，A2 只消费新 thread、内容互不串线。
- generic thread 可持久化且 elder_id=NULL；数据库与 Pydantic/TypedDict 均无非空冲突。
- greeting 在身份确定后由服务端发出，不等待 LLM；generic 走通用 greeting。

### T5 · ASR final 到回复的链路接线

**前置**：T1–T4 至少完成单元自验；A3 确认媒体 handler 调用 seam；A4/A1 的真实音频/ASR 服务可用或提供测试替身。

**执行步骤**

1. 将 A3 输出的 ASR FINAL 事件接入身份级联和 dialogue_service；PARTIAL 仍只更新字幕，不触发 LLM。
2. 身份判定先于上下文、LLM 与 TTS；voice/confirm/generic 使用对应服务端上下文。
3. 回复文本按 C2 tts_text 下发（带 C6 可选 degraded）；音频继续经既有 WebRTC track。
4. ASR 错误、LLM 超时和 TTS 失败分别使用既有 C2/C1 错误与降级边界；不更改 asr.py/tts.py/webrtc.py。
5. 与 A1 用真实 FunASR + 两个声纹 Mock 测试者完成身份→thread→LLM→TTS；声纹 spike 延迟时不得阻塞此联调。
