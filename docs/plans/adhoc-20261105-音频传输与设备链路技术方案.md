# 音频传输方案技术对比与设备语音链路实现设计

## 一、音频传输方案对比：WS 裸流 vs WebRTC 音频轨 + 信令 WS

### 1.1 逐维度对比

| 维度 | WS 裸音频流（教师模块形态） | WebRTC 音频轨 + 信令 WS（项目基线） |
| --- | --- | --- |
| 双工能力 | **半双工**：一条 WS 上行音频，TTS 下行要么另开 WS 要么复用排队，无法真正同时收发 | **全双工**：上行/下行两条 SRTP 轨同时流，说话与播报可并行 |
| 打断能力 | 差——打断要等当前"上传→识别→合成→回传"周期结束，延迟以秒计 | 说话即停写轨，打断延迟 ≈ 一帧（20ms 级） |
| 端到端延迟 | TCP 有序重传 + 队头阻塞：一个丢包卡住后续所有音频帧；且上行音频与下行 TTS 争同一条连接带宽 | UDP + jitter buffer：丢包容忍、乱序重排；目标 P95 ≤1.5s 才有达成空间 |
| 回声消除 | **致命短板**：TTS 经 `<audio>` 外放，麦克风回灌与说话信号混叠，长者不戴耳机（卧室平板外放是主场景），AEC 无联动、误识别率飙升 | TTS 经 WebRTC 轨下发，浏览器把输出与采集关联做 **AEC/AGC/NS**（constraints 一键开启） |
| 网络适应性 | 断线=整条连接报废，重连需重新走登录+建连 | ICE 自动切换 candidate、DTLS 会话内恢复，弱网抖动平滑 |
| NAT 穿透 | 无（浏览器直连服务器），内网/本机零成本；跨公网必须服务器公网可达 | 需 STUN/TURN 打洞——本机/局域网零成本，跨网段依赖 coturn（PRD §2.2 已配，教师提供拓扑） |
| 服务端实现 | 自研：收帧→重采样→喂 ASR→收 TTS→写回，协议自演进；aiortc 均不经过，CPU 开销集中在 Python 重采样 | aiortc 托管：RTP 解包/Opus 编解码/jitter buffer 全在库内；服务端只做"收轨→VAD→ASR、TTS→写轨" |
| 技术复杂度 | 低，半天可跑通（教师模块已验证） | 高——SDP/ICE/track 生命周期、aiortc loop 绑定（P1 风险）、状态机多 |
| 开发维护成本 | 短期低；长期协议自维护（重连、心跳、帧协议、多端兼容全自研） | 前期 steep（Day 3 主体成本），后期走 WebRTC 标准生态，多端（pad 平板浏览器）兼容性好 |
| 调试手段 | 抓 WS 帧即所见即所得 | 需 `chrome://webrtc-internals` + getStats，门槛略高 |

### 1.2 场景化结论（当前业务 = CCRC 长者卧室平板）

1. **外放扬声器是默认形态**（长者不戴耳机）→ 回声消除是硬前提 → 只有 WebRTC 轨能吃到浏览器 AEC 联动。这一条几乎单独定生死。
2. **全双工 + 可打断是 PRD 硬验收**（技术验收 line 1022）→ WS 裸流结构上做不到。
3. **WS 裸流的正确位置**：按住说话降级（PRD §2.2 已定，走 REST 整段上传）与调试抓流。它不是主链路候选，是降级链路本身。
4. **结论（与 day-03 v1.3 裁决一致）**：主链路 = WebRTC 音频轨 + 信令 WS（`signaling.py`）；降级 = REST 整段上传（`POST /api/audio/utterance`，T1）；常驻 PeerConnection、语音段级开合 ASR 会话（见 M3）。

## 二、M1 · 设备登录与音频采集设备初始化（最终版）

### 2.1 登录键方案（主理人最终裁决，v1.3：裁撤 device_code，直接用 device_id + device_secret）

**不新增任何字段、不建 device_code**。pad 登录凭证 = 既有 E4 契约的 `{device_id, device_secret}` 设备长期凭证——粘贴两串 UUID 走 `POST /api/device-sessions` 换证，零契约变更、零迁移、不触碰 auth 高风险区。device_id + device_code 的取舍：device_code 仅改善输入体验（8 位好输），对开发者粘贴操作无实际收益，且需迁移与契约修订；将来若真有输入体验需求，再加列只是一次小迁移，随时可加。

**业务流程顺序（硬约束，接口必须保证）**：

```
管理端创建老人账号（Day 2 elder CRUD 已就绪）→ 生成 elder_id
  → 管理端完成房间/设备绑定（Day 2 POST /api/devices/{id}/bind 已就绪），将 device_id + device_secret 交付设备
  → pad 登录页粘贴 device_id + device_secret → POST /api/device-sessions 换证
  → 声纹录入（Day 4，前置校验：elder 已创建且与会话身份一致）
```

注意：**只有 device_id 无法换证**——E4 契约要求 device_id 与 device_secret 成对提供；去掉 secret 即契约变更 + 单凭证泄露面问题（与已撤回的 elder_id 直连同类），不做。

**安全模型**：登录凭证 = device_id + device_secret（设备长期凭证，Day 2 双因子口径不变）；elder_id 始终由服务端从绑定关系读取，不作为登录键（禁区 9 口径不受影响）。

### 2.2 流程设计

```
pad 登录页粘贴 device_id + device_secret
  → POST /api/device-sessions（既有 E4 契约）
  → 200 { access_token, expires_in: 86400, device: {id, room_id, elder_id} }
  → 前端存 sessionStorage（不进 localStorage，防其他页面读取）
  → getUserMedia 初始化麦克风（constraints 见 2.3）
  → 成功：进主界面；失败：按 2.4 错误映射提示 + 重试
```

声纹录入（Day 4）在此之后：录入接口的 `elder_id` 从会话 token 解出（服务端按绑定关系读取），**与登录设备绑定关系天然一致**，不存在前后端字段错位；接口前置校验"elder 已创建 + 会话身份匹配"，流程顺序由服务端保证，不依赖前端自觉。

### 2.3 采集参数（constraints）

```js
{ audio: {
    deviceId: { ideal: savedDeviceId },   // 已绑定设备优先，插拔后回落默认
    echoCancellation: true,               // 外放场景硬前提（对比结论 1.2-1）
    noiseSuppression: true,
    autoGainControl: true,
    channelCount: 1,
    sampleRate: { ideal: 48000 }          // 浏览器采集 48k，下行 AudioWorklet 重采样到 16k（60ms/帧 PCM16，教师模块 audio-worklet.js 模式）
} }
```

- `navigator.mediaDevices.enumerateDevices()` 监听 `devicechange`：麦克风拔出 → 状态条提示 + 尝试回落默认设备重开。
- 采样链路统一 16k：采集 48k → AudioWorklet 线性插值重采样（复用教师模块实现，替换其"平均累加"为标准插值）。

### 2.4 错误映射与重试

| 错误 | 判定 | 提示口径 | 重试机制 |
| --- | --- | --- | --- |
| 编码不存在/已解绑 | HTTP 404 | "设备不存在，请检查 device_id 是否输入正确" | 输入框清焦可重输 |
| 设备已禁用 | HTTP 403 | "设备已被管理员停用，请联系工作人员" | 不重试 |
| 换证限流 | HTTP 429 | "尝试次数过多，请 1 分钟后再试" | 倒计时后解锁 |
| `NotAllowedError` | getUserMedia | "麦克风权限被拒绝：请点击地址栏图标允许后重试" | 显式重试按钮（重新 getUserMedia） |
| `NotFoundError` | getUserMedia | "未检测到麦克风设备" | 监听 devicechange 自动重试 |
| `NotReadableError` | getUserMedia | "麦克风被其他程序占用" | 重试按钮 |

重试统一走前端状态机：每次重试刷新 trace（沿用 `X-Trace-Id`），错误不静默吞。

## 三、M2 · 信令 WS 长连接（登录/心跳/重连）

### 3.1 端点与鉴权

- 端点：`WS /ws/signal`（实现时登记 README 端口表）。
- **首帧鉴权**（不用 query token，避免进访问日志）：连接后 300ms 内必须发 `{"type":"auth","token":"<device JWT>"}`；超时或验签失败 → 服务端回 `{"type":"auth_fail","code":"..."}` 后以 **4401** 关闭，写审计日志（复用 Day 2 `core/security` 三验签 + `devices` 回查；`elder_id` 只从库内绑定读，禁区 9）。
- WS 级 trace：accept 时生成 trace_id 注入连接上下文，贯穿该连接所有日志（TraceIdMiddleware 不覆盖 WS，信令层自补）。

### 3.2 心跳保活

- **应用层 JSON 心跳**（浏览器 JS 无法发 WS 协议级 ping，必须应用层）：
  - 客户端每 **20s** 发 `{"type":"ping"}`；服务端 45s 未收到任何帧 → 判死断开。
  - 服务端每 20s 发 `{"type":"ping"}`；客户端 45s 未收到 pong → 主动断开进重连。
  - 参数来源：`30s/60s` 为保守默认，最终值随弱网实测调整，登记 README。
- 心跳计数不与业务消息混用：任何合法帧都刷新对端活跃时间戳。

### 3.3 断线重连

- 前端状态机：`idle → connecting → authenticating → connected → reconnecting → closed`，状态条映射"正在听"等三态之外增加"连接中/已断开"。
- 指数退避：1s → 2s → 4s → 8s → 15s（封顶）+ 随机抖动 ±20%；**连续失败 5 次** → 状态条出"连接失败，点击重试"。
- 重连前检查 token 剩余有效期（24h 设备会话）：剩余 <10min 先静默调 `POST /api/sessions/refresh` 换新再重连；401 → 踢回登录页。
- `visibilitychange` 回前台立即触发一次重连（不等退避计时）。
- WebRTC 侧联动：WS 断开时 PeerConnection 保活不动（媒体流独立于信令）；WS 恢复后重发 ICE candidate 缓存。

## 四、M3 · VAD 触发通道建立与释放

### 4.1 通道生命周期（关键裁决复述）

**PeerConnection 常驻**（登录后建连一次，全生命周期保持），**随语音开合的是 ASR 会话**：

```
speechstart（TEN-VAD 判定人声）
  → 发 {"type":"asr_start"} → 服务端 start_session，preRoll 600ms 缓存帧随首帧补发
  → 逐帧 feed_audio（16k PCM16，60ms/帧）
speechend（静音 800ms）
  → 发 {"type":"asr_end"} → 服务端 finish()，等 offline final
  → ASR provider close、TTS 写轨队列清空 → 会话资源释放
maxSpeech 30s 强制切段（防长录音占资源）
```

PeerConnection 与音频轨不随静音断开——断开重连的握手成本（数百 ms~秒级）远高于维持空闲轨，且违背"全双工可打断"。

### 4.2 端侧主 VAD（TEN-VAD WASM，主理人裁决 v1.2）

- 移植教师模块 `BrowserTenVad`：`threshold`（默认 0.5）、`silence=0.8s`、`minSpeech=0.25s`、`maxSpeech=30s`；600ms preRoll（10 帧×60ms）保句首。
- WASM 拉取失败或初始化异常 → 前端打 `vad_mode=fallback` 标记 → **回落服务端 webrtcvad**：30ms 帧（`valid_rate_and_frame_length` 前置校验）、`mode=settings.webrtc_vad_aggressiveness`（默认 2）。
- 触发消息统一由前端发出（端侧 VAD 为主时）；兜底模式下前端只推流，服务端 VAD 自行判定 speechstart/speechend。

### 4.3 资源释放清单

静音/切段后必须释放：ASR 会话（provider.close）、TTS 合成任务（若在途）、服务端该会话帧缓冲；**不释放**：PeerConnection、音频轨、信令 WS、心跳计时。

## 五、M4 · 声纹采集与录入（实施批次：Day 4）

> **批次归属**：`voiceprints` 表与 `embedding` 列按 ER §6 属 Day 4（裁决 B2），Day 3 仅完成 CAM++ spike 留痕。本节为完整设计，Day 4 开卡直接实施。

### 5.1 采集流程（pad 端引导式）

```
录入向导（3 段式）
  每段：屏幕提示朗读固定句（如"今天天气真不错"）→ 录 ≥4s
  → 段内校验（5.2）不通过：给出具体原因，重录该段
  → 3 段全部通过：前端合并有效语音段 → 上传
  → 服务端：二次校验 → 逐段 CAM++ embedding（sherpa-onnx，3D-Speaker CAM++ 16k onnx，192 维，L2 归一化）
  → 向量均值 → 再归一化 → 落库 voiceprints（含 profile_revision = 模型 sha256）
```

### 5.2 音频质量校验（前后端双执行，参数可调）

| 校验项 | 阈值（初版，待标定） | 不通过提示 |
| --- | --- | --- |
| 有效语音时长（VAD 切段后） | ≥3s / 段 | "说话时间太短，请读完整个句子" |
| 有效语音占比 | ≥60% | "请靠近设备、连续说话，中间不要停顿" |
| 削波比例（|x|≥0.99 采样占比） | <1% | "离麦克风太近了，请稍微远一点" |
| 能量下限（RMS） | > -45dBFS | "环境太吵或音量太小，请到安静处重试" |
| 段间自一致（两两 embedding cosine） | ≥0.65 | "三次声音差异较大，请用正常音量重录"（说明有噪音/换人） |

段间自一致是防"录错人/环境突变"的关键闸门，阈值 0.65 为经验初值，Day 4 用真实录音标定后回填（同声纹阈值 0.85 的标定流程）。

### 5.3 标准化处理与安全边界

- 16k mono PCM16 进 embedding；**不落原始音频**（不触发 72h 保留规则；如需调试保存走 `audio_debug_save` 开关）。
- embedding 列维度以 Day 4 迁移裁决为准（CAM++ 192 维）；存 L2 归一化后的 float 向量，比对用 cosine（PRD §3.2 硬性数值 **≥0.85**）。
- `elder_id` 只从服务端设备 JWT 绑定解析（禁区 9）；录入接口走 `runtime_context` 身份，越权写审计。
- `profile_revision`（模型文件 sha256）随向量存库——模型升级后旧向量自动失效重录，防跨模型比对。

### 5.4 上传与接口口径（待开卡定义）

- 接口：`POST /api/voiceprints/enroll`（3 段音频 multipart）+ `POST /api/voiceprints/verify`（1 段，返回 `(matched, score, elder_id)`），契约文档 Day 4 开卡时按 §10.4 正式定稿——本节不冻结字段。
