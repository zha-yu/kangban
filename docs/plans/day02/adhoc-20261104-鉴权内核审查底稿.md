## 2. 先看全景：一个请求怎么变成身份

判定顺序是契约 §5.2 的八步落地，**顺序本身就是安全属性**（先验签再分派、先判存在再判角色）。

```
Authorization 头
  └─ bearer_token_from_header        auth.py:129   语法：只认 Bearer、恰好两段、非空 ASCII（S-23）
      └─ decode_principal_token      auth.py:156   固定顺序 access→device→staff_card 各完整验签（S-19）
          │                                          ※ 不读未验签的 typ 选分支
          └─ decode_token            security.py:614  验签 → exp（宽容 0）→ iat 提前量 ≤60s → 载荷白名单
                                               ↓ 签名有效但载荷自相矛盾 → TokenInvalidError（401，不是 500）
      └─ resolve_principal           auth.py:527   一类令牌只查一张表，库里事实喂给判定函数
          ├─ _load_staff_row         auth.py:444   role / status / token_version
          ├─ _load_guardian_row      auth.py:461   status / token_version
          ├─ _load_device_row        auth.py:476   token_hash / status / elder_id
          └─ _load_staff_token_row   auth.py:498   归属 + JOIN 员工状态 + JOIN 设备 elder_id
      └─ *_identity_from_*           auth.py:233/260/278/338  库里事实 vs 载荷逐项比对 → 构造 Identity
          └─ get_current_principal   auth.py:586   生成器依赖：set_identity → yield → finally reset（S-18 ③）
              └─ current_* / require_roles  auth.py:621-654  拿错主体种类 401（S-24）；角色不足 403
                  └─ runtime_context          工具层只从这里读 elder_id（TD 839，闸门③）
```

**审查这一步要问的三个问题**：

- [ ] 「多一个载荷字段即拒」是否**双向**成立？签发侧 `_build_payload`（security.py:365）与解码侧 `decode_token`（security.py:614）都调 `_validate_payload`（security.py:532）——只看一侧等于没防住「旧版本签出的令牌」。守卫：`test_decode_rejects_self_contradictory_payloads_even_with_a_valid_signature`（16 条）。
- [ ] 「库里事实优先于载荷」有没有被任何一处反向破坏？角色（S-20）、`token_version`、设备哈希、工牌到期都以库为准。**反向破坏**长这样：某处 `claims.get("role") or db_role`。请全文搜 `or db_`、`or claims`，应为 0 处。
- [ ] 四道门（验签→判存在→判角色→判范围）里，**范围过滤确实不在内核内**（计划 §3 边界；契约 S-17 要求长者范围由服务层按 `beds` / `elder_guardians` 判定）。`require_roles` 只管角色，`app/api` 不许指望它过滤长者范围。

### ④ `jwt_algorithm` 是配置项而不是常量（写底稿时新发现；实测**不构成漏洞**，但要你表个态）

`config.py:47` 为 `jwt_algorithm: str = "HS256"`，签发（security.py:361）与解码（security.py:633）读同一个值。
契约 S-04 写的是「算法为 HS256、单密钥」——那是**选型**声明，代码按字面理解成了**可配**。

我按「那要是有人把它配坏」实测了三种配错（pyjwt 2.15.1 / Python 3.12.7）：

| 配错值 | 后果 | 为什么拦住了 |
| --- | --- | --- |
| `none` | 解不出任何无签名令牌：`InvalidKeyError: When alg = "none", key value must be None` | 我们的密钥闸门（S-14）保证 `jwt_secret` 永不为空，`key=None` 这条路根本到不了 |
| `HS512` 等其它 HMAC | 能签能解，但两侧同源，令牌自报 `alg` 从不参与选择 → 不是算法混淆 | `test_other_hmac_algorithm_token_is_rejected`、`test_alg_none_token_is_rejected` |
| 空/短密钥 | 签发与解码双双拒（S-14） | `test_short_secret_is_refused` |

所以**剩下的不是攻击面，是口径问题**：一条安全参数可以在不改代码、不签发的情况下被 `.env` 改掉，
而 PRD/TD 从没授权这个自由度；换密钥轮换或多服务时它会变成真实的排查项。

- [ ] **钉成常量**（推荐）：`security.py` 用固定 `HS256`，`jwt_algorithm` 要么删要么仅作展示；契约 S-04 补一句「算法为常量，改它需翻案」。
      成本约 5 行 + 2 条用例，改动**全在本卡写作用域内**（`config.py` 属 task-1，需 A 同意才能删字段，所以我倾向于先在 `security.py` 里钉住、字段留着由 A 决定去留）。
      理由与 S-11 不给 bcrypt cost 留口子是同一条：**留了可改的口子，就等于留了「可被悄悄调弱」的口子**。
- [ ] **保持可配**：接受它，并在 S-04 登记「`jwt_algorithm` 属部署期参数，改它需评审」——把隐含的自由度变成显式的责任。

两条都要动契约（属口径变化，我不自行改）。
