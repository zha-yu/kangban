## 1. 项目目标

### 1.1 项目定位

面向 CCRC 康养社区长者卧室的 **3D 数字人陪伴系统**：浏览器页面（模拟平板）上的 VRM 数字人 + WebRTC 全双工语音，用「安全规则层 → Laya 端侧分类器 → 主控 Agent」三级路由，承担情感陪伴、用药提醒、健康数据采集、戏曲/天气检索与人工告警五类职责。**不做医疗诊断，不替代 SOS 紧急呼叫。**

### 1.2 三个使用端（同一仓库）

| 端 | 目录 | 视口 | 说明 |
| --- | --- | --- | --- |
| 长者端 pad | `frontend/src/pad/` | 1920×1080 大字 | 3D 数字人 + 语音 |
| 照护台 console | `frontend/src/console/` | 桌面 | 护工/医生/管理员按角色分流 |
| 家属端 family | `frontend/src/family/` | 375px 移动优先 | 家属查看 |

### 1.3 当前子任务：房间与床位管理（用户 2026-11-08 发起）

用户原始 7 条要求（逐条，不得删减）：

1. **功能范围**：房间 CRUD、床位 CRUD、房间与床位关联绑定、床位状态管理（空闲/占用/维修/停用）。
2. **权限**：仅超级管理员及拥有房间管理权限的管理员可访问。
3. **数据校验**：房间编号唯一、床位编号同房间唯一、必填非空。
4. **交互**：列表分页、按房间号/床位号/状态多条件筛选、批量操作入口、操作结果实时反馈。
5. **数据关联**：床位变更自动同步入住状态记录；删除房间前校验是否存在未清空床位。
6. **日志**：所有管理操作记录操作人、时间、变更前后内容。
7. **交付**：前后端接口 + 页面交互 + 单元测试覆盖 + 操作说明文档。

同时用户要求先做**异常排查**：截图里 `http://localhost:8000/health` 控制台报 `net::ERR_ABORTED`。

**排查结论（已完成，无需改代码）**：该接口本身返回 200，`ERR_ABORTED` 是请求被取消（页面刷新/导航/重复请求），不是后端 5xx；前端代码里没有任何 `/health` 调用。影响为零。真正的缺口是 admin 只有 E18 只读、没有写接口与审计。

### 1.4 本子任务完成定义

- 后端 10 个管理端端点 + 服务层 + 纯函数聚合 + pytest 覆盖。
- 前端管理页（筛选/分页/CRUD/批量/反馈）+ `pnpm build` 通过。
- 浏览器走查：admin 全流程通过，care_worker/doctor/guardian/device 一律 403 且不白屏。
- 文档：接口契约、PRD FR、TD/ER 修订记录、操作说明、计划索引。
- **不引入** Vitest / Testing Library / 组件库 / 路由库 / 状态库。

| ORM/迁移 | SQLAlchemy 2.x（async）+ Alembic | 分批迁移，**主迁移一经合入不再改** |
| 缓存 | Redis | 短期会话、限流、重复调用检测；不是长期记忆唯一存储 |
| 调度 | APScheduler | 用药到点、19:00 健康采集、日报、记忆归并、漏采派单、原始音频 72h 清理 |
| System One | Laya（本地开源权重，CPU 推理） | 一次前向出 intent / sensitive / confidence / privacy 四信号 |
| System Two | DeepSeek 或 Qwen 兼容 API | 经统一 LLM 适配器接入，不直连 SDK |
| Agent 编排 | 受约束 CompanionAgent（ReAct + Tool Calling） | 业务子图仅 2 个：`medication_confirmation_graph`、`health_checkup_graph` |
| 状态工作流 | LangGraph + PostgreSQL Checkpointer | 按 `thread_id` 持久化，支持 Interrupt/HITL 与断点恢复 |
| 工具协议 | MCP | `weather`（唯一真实外部接口）+ `mock-operations`（工单/通知，Mock 落库） |
| 观测 | Langfuse + OpenTelemetry Traces + `/metrics` | 全链路统一 `trace_id`；上传前脱敏 |
| 容器 | Docker Compose + nginx | 7 服务一键起；HTTPS 本地受控证书（getUserMedia 硬要求） |
| 包管理 | **uv**（后端）、**pnpm**（前端） | Windows 侧 `C:\Python313\Scripts\uv.exe` 实测 0.12.24 |

### 3.2 项目级红线（AGENTS §4，AI 不得自行决定）

1. 不连生产数据库、不连真实医疗系统；只允许 `docker compose` 起的本地 PostgreSQL。
2. 不硬编码任何密钥：API Key、JWT secret、数据库口令、TURN credential 一律经 Pydantic Settings 从 `.env` 读取；`.env` 已在 `.gitignore`，`.env.example` 只放占位符。

6. 不改已合入的 Alembic 历史迁移，只新增迁移文件。
7. 基线文档（PRD / 技术设计文档 / 大纲）**可以改正文，但不许静默改**：口径变化必须①在文末「修订记录」章节新增一条，写清「改了哪条、依据哪条裁决或 PRD 条款、影响哪些 FR/AC/表」；②正文改动与修订记录同一次提交。修订记录章节不存在时必须先补建，标题统一 `## 修订记录`，三列表 `| 版本 | 日期 | 说明 |`，版本号沿用文档现有最大值 +1，无历史则从 `v1.0` 起。**禁止**删改历史修订行、悄悄改版本号、改完正文不写记录。

### 5.5 `app/services/org_status.py`（未提交，新增）

纯函数，不查库不写库，管理端与 E19 共用：

```python
_UNAVAILABLE_STATUSES = frozenset({"maintenance", "disabled"})

def aggregate_room_status(bed_statuses: Iterable[str]) -> str:
    statuses = list(bed_statuses)
    if not statuses:                                   return "available"    # 无床
    if all(s in _UNAVAILABLE_STATUSES for s in statuses): return "maintenance" # 全维修/停用
    if all(s == "occupied" for s in statuses):         return "full"         # 全占用
    if any(s == "occupied" or s != "available" for s in statuses): return "partial"
    return "available"
```

五分支优先级即上述顺序：无床 → 全维修/停用 → 全占用 → 有占用或存在非可用床 → 全可用。

## 7. 业务规则与不变量

1. **房间状态只读**：`rooms.status` 由该房间全部床位状态聚合派生，**不提供任何手工改房间状态的入口**。增/删/改床位后服务层重算；E19 入床/换床后也重算。
2. **聚合优先级**（`aggregate_room_status`）：无床 → `available`；全 `maintenance`/`disabled` → `maintenance`；全 `occupied` → `full`；存在 `occupied` 或存在非 `available` 床 → `partial`；其余 → `available`。
3. **`occupied` 不可手工写**：`beds.status='occupied'` 只能由 `beds.elder_id` 派生。PATCH 显式传 `occupied` → 422；服务层再兜一道 422。
4. **占床不可降级**：`elder_id` 非空的床位，改任何状态 → 409（状态只能由入住关系决定）。占床**可以**改床号（不改占用语义）。
5. **删除床位**：要求 `elder_id IS NULL` 且 `status != 'occupied'`，否则 409。
6. **删除房间**：要求该房间**无床位**且**无设备引用**（任一存在 → 409），避免 FK 违约变 500。
7. **唯一性**：`rooms.room_no` 全局唯一（DB 约束 `uq_rooms_room_no` + 服务层预查）；`beds` 的 `(room_id, bed_no)` 唯一（跨房间同名床号允许）。
8. **必填非空**：房号/床号在 Pydantic 层 `min_length=1`；服务层再 `strip()`，全空白 → 422，**不得落库**。
9. **批量原子性**：先 `SELECT … FOR UPDATE` 取全 → 去重 → 逐条校验 → 全部通过才 flush；任一缺失（404）或占用（409）整批不动。
10. **审计与业务同事务**：每次成功写操作写一条 `audit_logs`；批量只写一条（`detail.bed_ids` + before/after 数组）。审计写失败则整笔回滚。
11. **审计内容边界**：`detail` 只有 `before` / `after` / `trace_id`（批量另有 `bed_ids`）；快照字段仅 `room_no` / `bed_no` / `status` / `elder_id`；**不含长者姓名等 PII**。
12. **审计动作名**：`room_create`、`room_update`、`room_delete`、`bed_create`、`bed_update`、`bed_delete`、`bed_batch_status`、`bed_batch_delete`。
13. **幂等语义**：本功能未实现幂等键（不同于用药的 `(resident_id, plan_id, scheduled_at)`）；重复提交会二次写入，前端靠按钮禁用防抖。
14. **E19 语义不变**：`assign_bed` 只新增「同步房间状态」副作用，不改请求/响应/冲突码。

## 11. 关键约束与命名规范

### 11.1 分层与写库

- `app/services/` 是**唯一写库层**；`api` / `audio` / `scheduler` / `graphs` 一律不直接操作 ORM 写数据。
- 依赖方向单向：`api | audio | scheduler | graphs → services → models`；任何模块不得横向 import。
- `app/api/` 只做：参数校验、权限/范围过滤、调 services、序列化响应。

### 11.2 提交规范

- Conventional Commits：`feat/` `fix/` `docs/` `refactor/` `test/` `chore/`。
- 一次提交只做一件事；正文中文说清「为什么」。
- 不提交 `node_modules/`、`.venv/`、媒体大文件、原始录音、`*.vrm`/`*.glb`。

### 11.3 代码约定

- 全量 type hint；I/O 一律 async；配置走 Pydantic Settings，**禁止 `os.environ.get` 散读**。
- 日志结构化，**每一行都带 `trace_id`**；禁止打印密钥、手机号、完整住址、身份证；脱敏工具集中在 `app/core/`。
- 时间存储一律 UTC，展示层转 `Asia/Shanghai`。
- 工具层失败四分类：参数错 → 回传模型重试并计入预算；目标不存在 → 如实告知不编造；临时错误 → 退避重试 ≤2 次后降级话术；越权 → 拒绝 + 审计 + `trace_id`。

### 11.4 前端约定（console / family）

- **不引组件库、路由库、状态库**；样式 `var()` 引用 `tokens.css`，**不硬编码 hex**。
- 三入口共用一套 Vite 配置；pad 的 three-vrm 不得进 console/family 构建产物。
- 错误文案用用户语言；不回显 `trace_id` / `detail` 原文。
- 弹窗复用 `.dlg-mask` / `.dlg-card` / `.dlg-title` / `.dlg-sub` / `.dlg-actions` / `.field` / `.field-label` / `.field-input` / `.field-error`。

### 11.5 数据库与迁移

- PostgreSQL 15 + pgvector；业务表与 LangGraph checkpoint 物理隔离（独立 schema `langgraph`、独立连接池）。
- 分批迁移，**主迁移一经合入不再改**；只新增迁移文件。
- 当前迁移链：`0001 → 0002 → 0003 → 0004 → 0005 → 0006 → 0007 → 0008 → 0009 → 0010`（head = `0010_day6_medication`）。
- CHECK 约束名不加双前缀；换名走原生 SQL。

### 11.6 文档产出规范（AGENTS §10）

- 所有计划落 `docs/plans/`；**不新建 `plan.md` / `todo.md` 这类游离文件**。
- 命名：`<类别>-<编号>-<主题>.md`，类别 `day` / `task` / `adhoc`；主题 ≤12 字；日期不进文件名（`adhoc` 除外）；编号补零两位。
- 文件头必填四行：状态/版本/日期、关联、上游依据（PRD 行号 ｜ TD 行号）、变更记录见文末。
- 新增计划必须**同一次提交**登记进 `docs/plans/README.md` 索引表。
- 废弃计划把文件头改成 `状态：已废弃`，**不删**。
- 进度看板 `docs/team_tasks/day<N>/PROGRESS.md` **自动生成，不要手改**；要动进度改任务卡的 `> 状态：` 行；状态取值只有 `未开始 / 进行中 / 已完成 / 已取消 / 待确认`。

### 11.7 四类文档分工（别互相越界）

| 位置 | 只回答 | 改动成本 |
| --- | --- | --- |
| `docs/team_tasks/` | 谁做、前置、写作用域、验收 | 低 |
| `docs/plans/` | 怎么做、分几步、谁负责哪步 | 低 |
| `docs/接口契约_*.md` | 对外口径：字段、判定、端点 | 高（走裁决 + 变更记录） |
| 三份基线文档 | 事实与验收 | 高（正文可改，必须同提交补修订记录） |

### 11.8 高风险文件清单（AI 生成后必须人工逐行读 diff）

`app/core/security.py`、`app/core/auth*.py`、`app/api/auth*.py`（auth）；`app/models/**`、`alembic/versions/**`（迁移与 schema）；`app/agents/tool_registry.py`、`app/agents/companion.py`、`app/mcp_client/**`、`app/core/runtime_context.py`（Tool 权限）；`mcp-servers/**`（MCP server）；`Dockerfile`、`docker-compose.yml`、`.dockerignore`（部署）；`app/router/safety.py`、`app/router/rules.py`（安全一票否决）；`app/graphs/**`（状态与断点恢复）；`.env.example`（配置泄露）。

> 本任务的 `app/services/org_service.py`、`app/api/admin_org.py`、`app/api/schemas/org.py` 虽不在清单内，但涉及**写库与权限门禁**，同样需要人工读 diff。老师抽查口径为 `auth` / `memory` / `mcp_client` 三处。

### 11.9 三次法则

同一个坑第 3 次出现，必须补进 `AGENTS.md §9 踩坑记录`（格式：日期 ｜ 现象 ｜ 根因 ｜ 铁律）。

### 11.10 给 AI 下任务的统一模板

`改哪些文件 → 验收命令 → 禁止触碰的文件 → 完成后报告 diff 摘要`。涉及高风险清单内文件时，**先出方案再落代码**。
