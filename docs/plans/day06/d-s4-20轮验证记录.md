## 3. 插话打断链路验证

**端到端打通证据（补测轮 14:57:43，response `d334a155`，2 段）**：

1. 段 0 播放中用户开口 → 前端 speechstart 本地立即停播（A2 裁决路径）；
2. 服务端 `playback barged`（turn `be3e0bb2`，generation 33，**cleared_frames: 202** —— 清掉约 4s 未播帧）；
3. 段 0 的 `played` ack 已先到达，随后 `response_ack_canceled`（ack_segment_id=0，即「最后已播完段」口径）到达服务端——dev-C 口径转达件③落地正确；
4. 新回复 `6909a224`（epoch 32）正常下发播放，无串音。

**首段未播完即打断（正式窗口 5 轮，`d94c245b` / `71bd1725` / `6a068ee9` / `b7deafcf` / `c3ebbb48`）**：均收到 `response_ack_canceled` 且 **ack_segment_id=-1**（一段都没播完，dev-C 口径确认值），前端 canceled 上报路径正确。

S7 复核补充（2026-11-10）：**D1 影响面升级**——`build_turn_context` 组装历史时产出 `{"role":"assistant","content":null}`（`assistant_delivered_text` 为 NULL），该 null 会进入每一次带历史的 LLM 请求，OpenAI 兼容接口可能直接报错或忽略；不止丢审计，实际污染上下文链路。见 docs/plans/day06/d-s7-上下文样例底稿.md §5①。域仍 dev-C（写锁 L6）。

**未达成项**：「播第 1 段插话 → 服务端 delivered_text 只到第 1 段」**无法验证**——见缺陷 D1（turn 终态全量不落库）。

## 5. 「没有停止」根因定性（补测轮时间线）

| 时刻（UTC） | 事件 |
| --- | --- |
| 14:56:34.76 | turn `1abad173`（问花园）turn_started，response `84e3974d` 2 段 |
| 14:56:42.5 | TTS 入队 10.3s，开始播放 |
| 14:56:52.8 | 播放结束（队列清空） |
| 14:56:56–14:57:25 | **用户说话**：服务端 webrtcvad 检出 14:56:56（4.6s）、14:57:07（10.4s）、14:57:14、14:57:19 等多段语音且均 delivery；**端侧 TEN-VAD 全程未触发 speechstart → 零 asr_start → 零 turn** |
| 14:57:29.47 | 端侧终于触发（`be3e0bb2`「这个太死了」），barged cleared_frames=0（此时早已无播放） |
| 14:57:39.96 | 回复 `d334a155` 下发播放 |

**结论**：打断停声机制本身工作正常；「没有停止/没反应」的实际根因是 **D3 端侧 TEN-VAD 漏检**——用户第一次插话发生在 14:56:56–14:57:25 的漏检窗口内，系统收不到任何信号。另注：`vad.ts` 头注释 threshold 0.5 与 Day4 收音优化记录（0.5→0.6）不一致，实际值以 `vad-assets/vad-worker.js` 构建产物为准，复测时核对。
