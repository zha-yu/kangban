# A12 · 工单建单服务接口设计（只定签名与幂等键，不落实现）

## 0. 为什么先定接口，而不是各写各的

本日有两个地方要建工单，而且**都不在对方的主线里**：

| 触发方 | 场景 | 工单类型 |
| --- | --- | --- |
| **dev-A（A12）** | 用药四次触达后 `missed_unconfirmed` | `missed_medication` |
| **dev-C（N27）** | 急症/敏感词一票否决（AC-04） | `sos` / `sensitive_alert` |

如果两边各写一份 `INSERT INTO work_orders`，会出现三个必然分叉：

1. **`order_no` 生成规则不一致** → console 列表上出现两种编号，护工无法口述报单号；
2. **`severity` 快照时机不一致** → 一个建单时抄、一个每次同步，看板的"红色单"数量对不上；
3. **重复建单** → 同一个漏服事件被 scheduler 重试建了 3 张单，护工一天接到 3 通同样的提醒。

所以：**`app/services/work_order_service.py` 是唯一建单入口，谁都不直接 `session.add(WorkOrder(...))`。**
这与 `app/services/` 是唯一写库层的既有约束（`AGENTS.md` §2）同源，不是新规矩。

## 1. 接口草案（待 C 确认后冻结）

```python
# app/services/work_order_service.py

@dataclass(frozen=True, slots=True)
class WorkOrderRef:
    order_id: uuid.UUID
    order_no: str
    status: str
    created: bool          # False = 命中幂等，返回既有单

async def open_work_order(
    session: AsyncSession,
    *,
    elder_id: uuid.UUID,
    order_type: str,                 # _ORDER_TYPE 八值
    severity: str,                   # red / yellow
    source_type: str,                # medication_event / risk_event / conversation_thread / device / None
    source_id: uuid.UUID | None,     # 幂等键的实体部分
    detail: dict | None = None,      # 只放 ID、枚举、时间；不放姓名/电话/原文
    actor_type: str = "system",      # staff / guardian / system
    actor_id: uuid.UUID | None = None,
) -> WorkOrderRef: ...

async def transition(
    session: AsyncSession,
    *,
    order_id: uuid.UUID,
    to_status: str,                  # acknowledged / in_progress / resolved / closed / reopened
    actor_type: str,
    actor_id: uuid.UUID | None,
    note: str | None = None,
    false_alarm: bool = False,
    false_alarm_reason: str | None = None,
) -> None: ...

# 便捷包装：只做参数映射，不另写建单逻辑
async def open_missed_medication(
    session: AsyncSession, *, elder_id: uuid.UUID, reminder_id: uuid.UUID,
    drug_name: str, scheduled_at: datetime, attempts: int,
) -> WorkOrderRef: ...
```

三个约束：

1. **不 commit，只 flush**（同 `audit_log_service` / `history_service` 口径）。事务边界由调用方定，
   这样「用药终态 + 工单 + 审计」才能同生共死。
2. **`detail` 只允许 ID、枚举、时间**。姓名、手机号、长者原话一律不进 `detail`（`work_orders.note`
   与 `detail` 都会被护工在 console 里看到，也可能进日志）。
3. **`transition` 是唯一的状态写口**，禁止别处直接 `UPDATE work_orders SET status=...`；
   否则 `work_order_transitions` 会漏行，工单时间线断掉。

## 2. 幂等键（这一节是核心）

`work_orders` 表**没有幂等列**，只有 `order_no` 唯一。所以幂等靠「**先查后建 + 唯一索引兜底**」：

```python
# 逻辑幂等键
dedupe_key = (elder_id, order_type, source_type, source_id)
```

- `source_id` **非空**时（正常路径）：同一位长者、同一类型、同一来源实体 → 视为同一张单。
  用药漏服取 `reminder_id`，急症取 `risk_events.event_id`。
- `source_id` **为空**时（无实体来源，如「设备离线」）：退化为「同类型 + 未终结」即复用，
  即 `status NOT IN ('resolved','closed')`，**而不是**用时间窗——时间窗会随重试漂移。

查重顺序（同一事务内）：

```
① 若 source_type='medication_event'：查 work_orders(elder_id, type, source_id) 未终结 → 命中即返回 created=False
② 若 source_type='risk_event'     ：同上，用 source_id（risk_events.event_id）
③ 未命中 → 生成 order_no → INSERT → 唯一索引冲突则回查一次并返回既有单
```

**必须加的索引（由 dev-C 并入 0011，见 §6）**：

| 索引 | 用途 |
| --- | --- |
| `ix_work_orders_elder_id_type_source_id` on `(elder_id, type, source_id)` | 幂等查重走索引，不扫全表 |
| `ix_work_orders_event_id` on `(event_id)` | 由 `risk_events` 反查工单（安全层与看板都要） |

> 现在 0010 只建了 `uq_work_orders_order_no`、`ix_work_orders_status_severity_created_at`、
> `ix_work_orders_elder_id_status`。缺上面两条，幂等查询会退化成 `work_orders` 全表扫——
> 演示数据看不出，接真实数据后每建一单扫一次。

### `order_no` 生成

```python
f"WO-{yyyymmdd}-{uuid4().hex[:6].upper()}"     # 例：WO-20261109-3F9A2C
```

- 用**建单日期**而不是 `created_at` 的时区敏感值，护工念单号时只关心"哪天的单"。
- 唯一性靠 `uq_work_orders_order_no` + **冲突重试 ≤3 次**，不靠"先查有没有重复"（那是竞态）。
- 不用数据库序列：那需要 0011 建 sequence，而 0011 归 C，本日不新增迁移面。

## 3. `severity` 是建单快照，不随后同步

`work_orders.severity` 建单时从来源**抄一份**，之后不跟着 `risk_events.severity` 变。
（0010 的列注释已定：「severity 为建单快照」）

理由：黄单升红单是**一次处置动作**，不是同一条记录的字段变更。若同步更新，看板上
「本周红色工单」会随风险事件升级而漂移，周报数字无法解释。升红走 `transition(reopened)` +
新建一条红单，两条单各自有自己的时间线。

## 4. 状态机（`transition` 的合法迁移）

```
new ──► acknowledged ──► in_progress ──► resolved ──► closed
 │            │                │              │
 └────────────┴────────────────┴──────────────┴──► closed（直接关闭，需 note）
                                    resolved/closed ──► reopened ──► in_progress
```

| 目标状态 | 前置状态 | 额外要求 |
| --- | --- | --- |
| `acknowledged` | `new` | — |
| `in_progress` | `acknowledged`、`reopened` | — |
| `resolved` | `in_progress` | — |
| `closed` | `new`、`acknowledged`、`in_progress`、`resolved` | 必须给 `note` |
| `reopened` | `resolved`、`closed` | 必须给 `note` |

**非法迁移抛 `InvalidTransition`（不静默忽略）**。静默忽略会让「护工点了关闭但没关掉」
这种问题永远查不出来。

两条硬规则：

1. **`false_alarm=True` 必须带 `false_alarm_reason`**，否则抛 `WorkOrderError`。
   误报关单要留下"为什么算误报"，否则事后无法区分"漏报"和"误报"。
2. **红色单必须有 `actual_handled_at`**（处置完成时写）。缺它，红色单的响应时长无法统计。

## 5. 两个调用方各自的参数映射

| 调用方 | `order_type` | `severity` | `source_type` | `source_id` | `dedupe_key` 退化说明 |
| --- | --- | --- | --- | --- | --- |
| **A12 漏服** | `missed_medication` | `yellow` | `medication_event` | `reminder_id` | 同一提醒事件只建一张单 |
| **C·N27 急症** | `sos`（红）/ `sensitive_alert`（黄） | `red` / `yellow` | `risk_event` | `risk_events.event_id` | 同一风险事件只建一张单 |
| Day 8 漏采 | `collection_missed` | `yellow` | `None` | `None` | 同长者同类型未终结即复用 |

### A12 侧的调用时机（写给我自己的约束）

```
finalize(terminal=missed_unconfirmed) → set_terminal(...) → open_missed_medication(...) → 图结束
```

**先写终态、再建单**。理由：终态是事实（"这次提醒确实没确认上"），建单是派单动作。
若建单失败，事实仍成立，scheduler 下一轮可凭终态补建；反过来先建单再写终态，
一旦终态写失败，就会出现"有工单但事件还是 calling"的悬空状态，得靠人工对账。
幂等键保证补建不会重复开单。

## 6. 需要 dev-C 并入 0011 的 DDL（本日 A/B 不新建迁移）

因 2026-11-09 裁决「0011 归 dev-C」（写锁 L11），上面两条索引以**请求**形式提交：

```sql
CREATE INDEX ix_work_orders_elder_id_type_source_id
    ON work_orders (elder_id, type, source_id);
CREATE INDEX ix_work_orders_event_id
    ON work_orders (event_id);
```

若要更强的幂等（并发也保证只有一张单），可再加：

```sql
CREATE UNIQUE INDEX uq_work_orders_source
    ON work_orders (elder_id, type, source_id)
    WHERE source_id IS NOT NULL AND status NOT IN ('resolved', 'closed');
```

> ⚠️ 这条**部分唯一索引**有副作用：一张单 resolved 后，同一来源可以再开新单（这正是我们要的），
> 但 `reopened` 的单与新单会同时存在。**如果 C 决定加它，A12 的调用顺序必须改成"先查未终结单"，
> 不能靠捕获冲突兜底**——否则 reopened 的场景会抛唯一键异常。我的建议：**先不加唯一索引**，
> 只加普通索引 + 先查后建，等真的有并发重复单的实测数据再加。

## 7. 验收判据（A12 落地时要能跑）

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 同一 `reminder_id` 连调两次 | 第二次 `created=False`，`order_id` 相同，`work_orders` 只有 1 行 |
| 2 | 并发两次（两个事务） | 最终只有 1 行；其中一个返回 `created=False` |
| 3 | `new → resolved`（跳步） | 抛 `InvalidTransition`，状态不变 |
| 4 | `closed` 不带 `note` | 抛 `WorkOrderError` |
| 5 | `false_alarm=True` 无原因 | 抛 `WorkOrderError` |
| 6 | 任意一次 `transition` | `work_order_transitions` 多一行（`from_status`/`to_status` 正确）+ `audit_logs` 一行 |
| 7 | `detail` 里塞长者姓名 | 调用方自测：序列化前应被上层拒绝；服务层只存 `detail`，不二次校验（**约定**，不在代码里拦） |
