## 1. 主体与身份模型

系统里可被识别的主体共 5 类（PRD §3.1 line 172-178 + TD line 349-406）：

| 主体 | 存储 | 登录方式 | 说明 |
| --- | --- | --- | --- |
| `admin` 管理员 | `staff_accounts.role='admin'` | 手机号 + 密码 | 维护演示数据与配置 |
| `care_worker` 护工 | `staff_accounts.role='care_worker'` | 手机号 + 密码 | 只看 `elder_staff_assignments` 里 `relation='primary_care'` 的长者 |
| `doctor` 医生 | `staff_accounts.role='doctor'` | 手机号 + 密码 | 只看 `relation='doctor'` 的长者 |
| `guardian` 家属 | `guardian_accounts` | 手机号 + 密码 | 只看 `elder_guardians` 里 `status='active'` 的日报（PRD 410 FR-RPT-02） |
| `device` 设备 | `devices` | 长期设备令牌换会话 | 代表一台平板；身份第一锚点（TD 311） |

**长者本人不登录。** 长者身份靠「设备绑定圈定候选集 + 声纹 cosine≥0.85」双条件判定，属 Day 4 范围（PRD §3.2 line 182-195），本契约不涉及。

## 3. 操作与判定（判定行 · 全量取自 PRD）

| # | 操作 | 允许主体 | 拒绝条件 → 结果 | PRD 出处 |
| --- | --- | --- | --- | --- |
| O1 | 账号密码登录 | 四类人账号 | 密码错 → 401；`status='disabled'` → 401 | 180 |
| O2 | 刷新凭证 | 持有效 refresh 者 | 类型不符 / 已失效 → 401 | 180 |
| O3 | 读当前身份 | 任一已登录主体 | 无凭证 / 凭证无效 → 401 | FR-ADM-03（437） |
| O4 | 设备换会话 | 设备 | 未绑定 / 已解绑 / 令牌哈希不符 → 401 | 89、180 |
| O5 | 长者增、改、停用 | **仅 admin** | 非 admin → 403 | 178、FR-ADM-01（435） |
| O6 | 读单个长者 | admin 全量；护工/医生限本人 `relation` 关联 | 范围外 → 403 + 审计 | 175/176、AC-18（499） |
| O6′ | 家属读长者档案 | **禁止**（见裁决 A-01） | 一律 403 + 审计 | 177 白名单不含档案、FR-RPT-02（410） |
| O7 | 长者列表 | 同 O6，只返回范围内 | 无范围 → 空列表（不是 403） | AC-18（499） |
| O8 | 设备绑定 / 解绑 | 仅 admin | 解绑后旧设备会话 → 401 | FR-ADM-01（435）、AC-24（505） |
| O9 | 设备候选长者 | 设备自身 | 无绑定 → 401 | 89、186 |
| O10 | 员工 / 角色维护 | admin | 改 `role` 或 `status` → `token_version+1`，旧 token → 401 | FR-ADM-01（435）、180 |
| O11 | 家属绑定 | admin | 超 2 位 → 409 | FR-ADM-02（436）、396 |
| O12 | 工牌换受限令牌 | 护工 + 设备 | 过期 → 401 | FR-ADM-08（442） |

**四类拒绝必须分清**（不是同一个 4xx）：

| 情形 | 码 | 谁的责任 |
| --- | --- | --- |
| 没带凭证 / 签名错 / 过期 / `token_version` 被提 | 401 | 凭证本身失效 |
| 凭证有效但角色不够 | 403 | 主体不符 |
| 凭证有效、角色够，但目标不在范围内 | 403 + 审计 | **范围越权（AC-18）** |
| 目标 `elder_id` 根本不存在 | 404 | 资源不存在，不泄露存在性给范围外主体（先判范围，再判存在） |

> 顺序固定：**验签 → 判角色 → 判范围 → 判存在**。范围外的人看不到 404，统一得到 403。

## 4. 端点（自裁行 S-01：全部路径无文档依据，服务端自定）

前缀 `/api`（裁决 A-03）；`/health` 例外留在根，供 Docker healthcheck 直连（AGENTS §3）。

### E1 `POST /api/sessions` — 人账号登录

```jsonc
// 请求
{ "phone": "13800000001", "password": "……" }
// 200：access 2h / refresh 7d（PRD 180）
{
  "access_token": "…",
  "refresh_token": "…",
  "token_type": "bearer",
  "expires_in": 7200,
  "principal": { "kind": "staff", "id": "uuid", "role": "care_worker", "name": "王护工" }
}
```

- 401 密码错 / 账号 `disabled`；422 字段缺失或格式错。
- `staff` 与 `guardian` 共用此端点，服务端按手机号先查 `staff_accounts` 再查 `guardian_accounts`；两表都有该号 → 409（S-02 唯一约束保证不冲突）。

### E2 `POST /api/sessions/refresh`

```jsonc
{ "refresh_token": "…" }   // → 200 { "access_token": "…", "expires_in": 7200 }
```

- 401 类型不符、已过期、`token_version` 不匹配。

### E3 `GET /api/sessions/current`

```jsonc
// 200
{
  "kind": "guardian", "id": "uuid", "role": null, "name": "张女士",
  "scope_elder_ids": ["uuid-a"]        // 家属=elder_guardians; 护工/医生=elder_staff_assignments; admin=[]
}
```

- 家属端靠这个字段显示"我绑定的是谁"，**不额外开档案接口**（裁决 A-01）。

### E4 `POST /api/device-sessions` — 设备换会话

```jsonc
{ "device_id": "uuid", "device_secret": "长期令牌明文" }
// → 200 { "access_token": "…", "expires_in": 86400, "device": { "id": "uuid", "room_id": "uuid", "elder_id": "uuid|null" } }
```

- 服务端 `sha256(secret)` 与 `devices.token_hash` 比对（S-03）。
- 401 不匹配 / 设备 `locked` / `elder_id` 为 NULL 且房间内无在住长者。

### E5 `POST /api/elders` — 长者建档（admin）

```jsonc
{ "name": "张桂芬", "birth_date": "1948-03-12", "gender": "female", "persona_id": "uuid|null" }
// → 201 { "elder_id": "uuid", "status": "active", "session_seq": 0, "created_at": "…" }
```

- 403 非 admin → 审计；422 字段格式错；409 无（`name` 不唯一，允许重名）。

### E6 `GET /api/elders/{elder_id}`

- 200 返回 R4 全字段 + `room_no` + `bed_no`（由 `beds` JOIN 得出，S-05）。
- **403 家属**（A-01）、403 非负责护工/医生（AC-18）、404 不存在（仅对范围内主体）。

### E7 `GET /api/elders?page=1&page_size=20&status=active`

```jsonc
// 200
{ "items": [ { "elder_id": "uuid", "name": "张桂芬", "room_no": "A-301", "bed_no": "1 号床", "status": "active" } ],
  "total": 1, "page": 1, "page_size": 20 }
```

- 列表**不返** `birth_date` / `gender` / `persona_id`（S-07）。

### E8 `PATCH /api/elders/{elder_id}`

- 可改 `name` / `birth_date` / `gender` / `persona_id` / `status`；403 非 admin；404；422。
- `status='archived'` 只允许改状态，且需后续清理流程（FR-ADM-09，Day 8+），本轮只落状态。

### E9 `POST /api/devices/{device_id}/bind`

```jsonc
{ "room_id": "uuid", "elder_id": "uuid|null" }
// → 200 { "device_id": "uuid", "room_id": "uuid", "elder_id": "uuid|null" }
```

- 403 非 admin；404 设备不存在；409 该长者已绑其他设备（`uq_devices_elder_id`）/ 长者不在该房间的床位里。

### E10 `POST /api/devices/{device_id}/unbind`

- `elder_id` 置 NULL、`status='offline'`、轮换 `token_hash`（S-03：轮换即旧会话失效）。
- 403 非 admin；404。

### E11 `GET /api/devices/{device_id}/elder-candidates`

```jsonc
// 200
{ "room_id": "uuid", "mode": "single|double",
  "candidates": [ { "elder_id": "uuid", "bed_no": "1 号床", "display_name": "张*芬" } ] }
```

- 候选来源：`beds WHERE room_id=设备房间 AND elder_id IS NOT NULL`，单人间 1 位、双人间 2 位（PRD 89、186）。
- `display_name` 走脱敏：姓 + `*` + 末字（S-06）。

### E12 `POST /api/staff`、`PATCH /api/staff/{staff_id}` — 员工维护（**已实现 2026-11-06**）

```jsonc
// POST 建档
{ "name": "李医生", "role": "doctor", "phone": "13700000003",
  "password": "Doctor@2026", "elder_ids": ["uuid"] }
// → 201 { "staff_id": "uuid", "name": "李医生", "role": "doctor",
//         "status": "active", "phone_masked": "137****0003" }

// PATCH 改角色 / 停用（二选一或同时）
{ "role": "care_worker" }  // 或 { "status": "disabled" }
// → 200 { 同上，role/status 已变 }
```

- 建档：`{name, role, phone, password, elder_ids?}`；`role ∈ admin|care_worker|doctor`，`phone` 为 11 位手机号，`password` 8–128 位。
- `elder_ids` 写 `elder_staff_assignments`（**补齐缺口 G2**：此前该表无任何写入口，导致新建 doctor 看不到任何长者）；映射 `doctor → doctor`、`care_worker → primary_care`，给 `admin` 分配长者一律 403。
- 改 `role`/`status` 时 `token_version+1`（O10），旧 Token 立即失效（AC-24）。
- 403 非 admin；409 手机号已存在（跨 `staff_accounts` 与 `guardian_accounts` 两表查重）；404 员工或长者不存在；422 口令/手机号不合法。
- 响应只回 `phone_masked`，不回传完整号码与口令哈希。

### E13 `POST /api/elders/{elder_id}/guardians` — 家属绑定（**已实现 2026-11-06**）

```jsonc
{ "guardian_id": "uuid", "relation": "女儿" }
// → 201 { "elder_id": "uuid", "guardian_id": "uuid", "relation": "女儿", "status": "active" }
```

- 409 已绑 / 超 2 位；404 长者或家属不存在；403 非 admin。
- 「≤2 位监护人」是**服务层校验**（只数 `status='active'` 的绑定），库表无约束（见 D6 已知缺陷）；`unbound` 的旧绑定不占名额。

### E15 `POST /api/guardians` — 家属建号（**已实现 2026-11-06**，补齐缺口 G1）

```jsonc
{ "name": "张女士", "phone": "13900000005", "password": "Fam@2026" }
// → 201 { "guardian_id": "uuid", "name": "张女士", "status": "active",
//         "phone_masked": "139****0005" }
```

- 原契约只有 E13「绑定已有家属」，**没有创建家属账号的端点**（缺口 G1）；家属账号不能由家属自助注册（与权限模型冲突），只能由管理员建。
- 409 手机号已存在（跨两表查重）；403 非 admin；422 口令/手机号不合法。
- 建号与绑定是两步：先 E15 拿到 `guardian_id`，再 E13 绑定到长者。

### E14 `POST /api/staff-cards` — 工牌换受限令牌（**Day 9 实现**）

```jsonc
{ "staff_card_code": "…", "device_id": "uuid" }
// → 201 { "token": "…", "scope": ["workorder:handle"], "expires_at": "…" }
```

- 落 `staff_tokens`（哈希存）；本契约只定字段与载荷，不打接口（裁决 A-04）。

## 5. 凭证设计（自裁行 S-03 / S-04）

### 5.1 三类载荷

| 凭证 | 载荷 | 有效期 | 失效靠 |
| --- | --- | --- | --- |
| 人员 access | `{sub:"staff:<id>"｜"guardian:<id>", kind, role, tv, typ:"access", iat, exp}` | 2h | `tv` 与库中 `token_version` 不等 |
| 人员 refresh | `{sub, kind, tv, typ:"refresh", iat, exp}` | 7d | 同上 |
| 设备会话 | `{sub:"device:<id>", kind:"device", dev, tv:"<token_hash 前 16 位>", typ:"device", iat, exp}` | 24h | 每次请求回查 `devices.token_hash` |
| 工牌受限 | `{sub:"staff:<id>", kind:"staff_card", dev, scope:[…], typ:"staff_card", iat, exp}` | 短时效 | `staff_tokens.expires_at` |

### 5.2 校验顺序（`app/core/auth.py` 实现口径）

```
1. 解 token，验签名与 exp           → 失败 401
2. 按 typ 分派：access 走主体表；device 走 devices；staff_card 走 staff_tokens
3. access/refresh：比对 tv 与 token_version → 不等 401（账号停用/改角色/解绑）
4. device：sha256 回查 token_hash 前缀 → 不等 401（解绑/轮换）
5. staff_card：查 staff_tokens 且 expires_at > now → 过期 401
6. 主体 status != active → 401
7. 组装 Principal 塞进 runtime_context（TD 168：app/core 输出"鉴权主体、上下文"）
8. 角色/范围判定交给依赖或服务层 → 403
```

### 5.3 设备两层凭证（为什么是两层）

- **长期层**：管理员建号时生成明文一次、只把 `sha256` 写进 `devices.token_hash`（TD 318「只存哈希不存明文」）。
- **会话层**：平板首次拿长期令牌换 24h 会话（PRD 180「模拟设备凭证换取会话，有效期 24h」）。
- 这样"解绑即失效"不需要黑名单：解绑轮换哈希 → 所有会话的 `tv` 对不上 → 401（AC-24）。

| S-26 | 缺 `Authorization` 头由鉴权内核产生 401，不许落到框架的 422 | `get_current_principal` 的头参数必须写成 `authorization: Annotated[str \| None, Header()] = None`（有默认值，故排在参数表末尾）。只写 `Annotated[str \| None, Header()]` 时 FastAPI 把该头当**必填参数**，缺头直接返回 422 `{"type":"missing"}`，`bearer_token_from_header` 根本不会被调用 | §7 已定「凭证缺失 = 401 `TOKEN_INVALID`」且 422 只留给 Pydantic 请求体校验；框架层的必填校验先于我们的解析器，等于绕过 §7 的码表。这条只在真实 ASGI 请求里暴露（直接调用依赖函数的单测看不到），因此用例必须带一条 `TestClient` 链路 | 若改用中间件统一解析头（不走依赖），必须给出等价的「缺头 401 而非 422」用例后才许改动本条 |

## 9. 裁决记录（PRD 内部或 PRD×TD 之间的歧义）

### A-01 家属能否读长者档案

- **冲突**：PRD 177 家属白名单只有「健康日报与需关注事件摘要」；PRD 499 AC-18 却把「请求 B 的详情」列为越权场景，读起来像"已绑定就能看详情"。
- **裁决**：按 177 白名单判**禁止**，家属读任何长者档案一律 403 + 审计。AC-18 的考点是"未绑定就拒"，不是"已绑定就许"。
- **替代方案**：家属端显示绑定长者姓名，走 `GET /api/sessions/current` 的 `scope_elder_ids`（E3），日报接口自带展示名。
- **翻案条件**：主理人认定 AC-18 隐含授权 → 改为"已绑定可读"，字段只放 `elder_id/name/room_no/status`，其余 403。

### A-02 AC-24 要求"审计保留"但审计表在 Day 9

- **裁决**：本轮写结构化日志（含 `trace_id`、主体、目标、结果），并在服务层留 `audit_action` 常量；Day 9 建 `audit_logs` 后补写库，历史从日志反灌可接受（教学数据）。
- **翻案条件**：评审要求 Day 2 就有可查询审计 → 提前建 `audit_logs`（需改批次表，要先改 ER）。

### A-03 路径前缀

- **裁决**：统一 `/api`，**不带 `/v1`**。理由：本项目不存在并行两版；统一前缀只为一件事——nginx 一条 `location /api/` 覆盖全部后端，Day 3 的 `/ws` 另开一条；`/health` 留根供健康检查。
- **翻案条件**：出现需要并存的第二版 API 时才加版本号，届时 `/api/v2` 前缀加一层 location 即可。

### A-04 工牌令牌本轮做到哪

- **裁决**：FR-ADM-08 是 P1，本契约只定字段（R9）与载荷（§5.1），`staff_tokens` 随 `0002` 建表；接口 E14 标 Day 9。
- **翻案条件**：演示需要现场刷工牌 → 提前实现 E14。
