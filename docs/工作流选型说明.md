# 工作流选型说明

> 本文件是大纲课时 1.4 的指定交付物：「把哪些用直线、哪些用状态图、各自状态字段和分支条件写进 `docs/工作流选型说明.md`」。
> 判据取自技术设计文档 §5（Workflow vs Agent 选型）与 PRD §2.4（能力→实现形态），**不按技术偏好选型**。
> 冲突仲裁：PRD 定「必须做成什么形态」，技术文档定「怎么实现」，两者冲突以 PRD 的验收为准。

---

## 1. 一句话判据

**看流程形态，不看技术时髦**：流程是直线（无回退、无循环、无人工卡点）就手写路由；
出现「重试循环 / 条件分支 / 副作用 / 人工确认」四者之一，且状态需要跨请求存活，才上状态图。

---

## 2. 四问决策法

| # | 问题 | 答「是」的后果 |
| --- | --- | --- |
| Q1 | 同一件事会**重复尝试**（重试 N 次、等回执超时再来一次）吗？ | 需要持久化「第几次了」，否则进程重启就丢 |
| Q2 | 存在**互斥分支**且分支后的路径不同（轻微/中等/严重 → 三种处置）吗？ | 需要显式分支节点，散在 `if` 里会失控 |
| Q3 | 有**不可回滚副作用**（建工单、推送家属、写风险事件）吗？ | 需要幂等键 + 断点恢复，不能靠函数调用顺序保证 |
| Q4 | 有**人工确认后才能继续**的卡点（HITL）吗？ | 必须能挂起、落 checkpoint、等人回来恢复 |

**四问全否 → 直线（FastAPI 路由 / 服务函数）。有一项为是 → 状态图（LangGraph）。**

补充约束（技术设计文档 §7.3，只保留两个业务子图的原因）：不用「能力多不多」判断，
而用「是否需要跨请求状态 + 断点恢复」判断；能用一个确定性 Workflow 加数据库状态列解决的，
不要引入图。

## 3. 本项目的形态映射（9 类能力）

| 能力 | 形态 | 为什么 | 落地课时 |
| --- | --- | --- | --- |
| 对话主链路（唤醒→ASR→路由→LLM→TTS） | **直线** | 无回退、无跨请求状态；套图只会增加延迟与调试成本 | Day 5–6 |
| 天气查询 | MCP Tool `get_weather` | 单次调用、无状态；规则层或主控 Agent 直接调用 | Day 6.3 |
| 戏曲/电影点播 | 普通 Tool + 媒体清单 | 单次查表 + 播放，失败重试由工具层兜底 | Day 6 |
| 长期记忆召回 | Memory Tool（pgvector） | 检索即返回，不构成流程 | Day 9 |
| **用药确认** | **LangGraph 子图** `medication_confirmation_graph` | Q1 有（T0/+5/+10/+15 四次，每次等 60s）、Q3 有（写事件 + 推送家属）、Q4 有（等回执/人工确认） | Day 7 |
| **健康采集与决策** | **LangGraph 子图** `health_checkup_graph` | Q1 有（未答可续问）、Q2 有（红/黄/绿三级处置）、Q3 有（风险事件 + 工单）、Q4 有（红标必须人工介入） | Day 8 |
| 工单流转 | 确定性 Workflow + 状态机列 | 状态流转在 `work_orders.status` 与 `work_order_transitions` 里，不需要图 | Day 9 |
| 家属通知 | MCP Tool `send_family_notification` | 幂等键 + 重试即可，无需跨请求记忆（重试由调度器承担） | Day 9 |
| 日报生成 | APScheduler 定时任务 | 无交互、无分支等待 | Day 9 |

> 口径来源：PRD §2.4「一个能力只允许一种形态」，已写进 AGENTS.md §4 禁区 8。

## 4. 两个子图的状态字段与分支条件（Day 7/8 落地前的约定）

### 4.1 `medication_confirmation_graph`

| 状态字段 | 类型 | 含义 |
| --- | --- | --- |
| `elder_id` / `plan_id` / `scheduled_at` | 服务端注入 | 幂等三元组，**不接受模型自报** |
| `attempt_no` | int 1–4 | 当前是第几次触达（T0/+5/+10/+15） |
| `last_attempt_at` | datetime | 用于 60s 等待窗口判定 |
| `reply` | `taken` / `refused` / `unclear` / `none` | 本轮识别的长者回应 |
| `outcome` | `taken_reported` / `refused` / `missed_unconfirmed` / `notification_failed` | 终态四值（PRD §4.5） |
| `work_order_id` | uuid? | 拒服或异常时的跟进工单（`type='follow_up'`） |

**分支条件**

1. `reply == taken` → 终态 `taken_reported`，结束。
2. `reply == refused` → 终态 `refused`，建 `follow_up` 工单 + 通知家属。
3. `reply in (unclear, none)` 且 `attempt_no < 4` → 等 60s → `attempt_no += 1` 回边。
4. `attempt_no == 4` 仍无回应 → `missed_unconfirmed`（**有回执无响应，不得写「实际漏服」**）。
5. 四次触达均无任何回执（设备侧失败）→ `notification_failed`，告警运维。

### 4.2 `health_checkup_graph`

| 状态字段 | 类型 | 含义 |
| --- | --- | --- |
| `elder_id` | 服务端注入 | 长者 |
| `slot` | `systolic`/`diastolic`/`sleep_hours`/`mood_score`/`complaint` | 当前问第几项（5 问对应 5 字段） |
| `answered` | dict | 已采集字段及其原文 |
| `parse_failures` | int | 连续解析失败次数（≥2 转人工，不落库） |
| `severity` | `red` / `yellow` / `green` | 分级结果 |
| `rule_version` | str | 判定规则版本，写进 `health_records` |

**分支条件**

1. 任一字段未答且未超窗口 → 重问该项（最多 2 次，再失败转人工）。
2. 采集齐 5 字段 → 计算 `severity`：
   - 红：收缩压 ≥180 **或** 舒张压 ≥120（单分量即判红）；
   - 黄：越界但未达红标，或 `mood_score ≤ 2`，或 `complaint` 命中不适关键词；
   - 绿：其余。
3. `severity == red` → 写 `risk_events` + 建 `health_alert` 工单 + 立即通知家属（**人工介入**，不走 TTS 随访话术）。
4. 19:00 窗口起、20:00 强制结束（`HEALTH_CHECKUP_START/END`），超窗未完成 → 记漏采并派单。

## 5. 反例：什么不该上状态图

- **对话主链路**：一次请求内完成，无跨请求状态 → 上图层只是把延迟从 1 处变成 3 处。
- **天气/戏曲查询**：单次工具调用，失败由工具层四分类处理 → 图无法带来任何收益。
- **能用数据库状态列表达的流转**（工单状态机）→ 状态列 + 服务层校验已经满足「可恢复」，加图反而两套状态源。

## 6. 什么信号出现时应该升级为状态图

上线后若出现以下任一现象，回看本文件并考虑改造：
① 同一业务在多个接口里各自维护「进度」字段；② 出现「进程重启后任务停在半路」的工单；
③ 某个流程里 `if severity == ...` 开始出现三层以上嵌套；④ 需要人工在中间步骤介入。
