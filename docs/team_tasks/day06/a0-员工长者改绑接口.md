## 背景

护工/医生与长者的绑定目前只有两个写入口：

1. **建号时分配**：`POST /api/staff`（E12）带可选 `elder_ids`，按 role 映射
   relation（`care_worker → primary_care` / `doctor → doctor`）写入
   `elder_staff_assignments`（staff_service.py L182-L187）；
2. **角色互转联动**：`PATCH /api/staff/{id}` 改 role 时同步翻转该员工全部
   assignment 的 relation（staff_service.py L225-L239）。

**没有「事后单独调整绑定」的入口**：长者换责任护工、医生调整负责名单、
离职员工交接长者——目前只能删号重建（会连带丢账号历史），属于范围过滤
唯一依据表（AGENTS §0 权限口径）的功能缺口。

## 待办

1. 契约先行：在 `docs/接口契约_身份与权限.md` 新增改绑端点（建议
   `PUT /api/staff/{staff_id}/elders`，admin only，全量覆盖式替换该员工的
   `elder_ids`；relation 仍按当前 role 映射，admin 一律 403），走冻结流程
2. 服务层 `staff_service.reassign_elders()`：事务内 diff——新增写入、
   缺失删除；保留 `UNIQUE(elder_id, staff_id, relation)` 兜底；写 `audit_logs`
   （改绑属高危权限操作，记录 trace_id + 操作者 + 前后差集）
3. 「每位长者 ≥1 责任护工」服务层校验（裁决 C4）在删除路径上必须生效：
   移除后若某长者失去全部 primary_care → 409
4. console `AdminUsersPage` 员工列表加「调整负责长者」操作，复用现有
   长者候选多选（真实 E7 数据，不臆造 elder_id）
5. 验证护工 token 范围：改绑后旧 token 的 `scope_elder_ids` 变化是否符合
   契约口径（逐请求查表 vs 重登生效），两害取其一并写进契约

## 验收

- admin 可在 console 上把某长者的责任护工从 A 换成 B，改绑后 A/B 各自
  登录，长者列表范围随之变化
- 非 admin 调改绑接口 403；移除最后一位责任护工 409
- `audit_logs` 可查到该次改绑（操作者、trace_id、差集）
- `uv run pytest -q` 通过，改绑服务层测试覆盖 403/409/diff 三路径
